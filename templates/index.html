STEP 02 — ATTESTED ACCESS

Decrypt

Server mints a single-use challenge, the recipient device authorizes it with its own private key, and the server verifies first — only then releasing a fingerprinted copy (text layer + LatticeMark pixel lattice) as a PENDING block needing 2-of-3 witnesses. No custodial keys, no silent release's key, and appends it to the ledger.

REFERENCE

How it works

The cryptographic reasoning behind attribution, in the order it happens.

1

Hybrid encryption

AES-256-GCM encrypts the document once. ML-KEM-768 protects recipient-specific access to that document key — one envelope per recipient, one shared ciphertext.

2

Decryption provenance

Each decryption creates a unique random event ID and an opaque random watermark token, embedded invisibly in that recipient's copy at decryption time.

3

Cryptographic evidence

The event record — who decrypted, which document, which watermark — is signed with the recipient's ML-DSA-65 private key.

4

Immutable record

Signed events are linked through a SHA-256 hash chain. Editing, reordering or deleting any past record breaks verification for everything after it.

5

Leak investigation

The watermark is extracted from a leaked PDF and matched against the signed ledger record — attributing the decryption event, never claiming who physically leaked the file.
